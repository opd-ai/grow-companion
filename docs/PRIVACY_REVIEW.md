# Grow Companion Privacy and Security Review

Review date: 2025-06-14
Scope: Current repository implementation and the supplied product specification. This is an engineering review, not legal advice. Where the specification promises a mechanism that is absent from the repository, the finding treats that silence or mismatch as a gap rather than assuming an unimplemented service exists.

## 1. Executive summary

The current build is strongly local-first: there is no network, CloudKit, analytics, widget, Watch, Siri, or third-party telemetry implementation in the repository; journal images are re-encoded without EXIF and stored with complete file protection; notifications default to generic lock-screen copy; and the app-switcher cover is implemented as a separate window. These controls are useful but do not yet support every security commitment in the specification. The highest-risk gaps are the lack of the promised signed rule-pack and encrypted-sync mechanisms, a fail-open app lock path when no device authentication policy is available, and incomplete export/delete coverage for newer records such as treatments and equipment. Offline correctness is currently local persistence rather than a tested multi-device sync design, so conflict resolution, clock skew, replay, and cloud deletion guarantees remain unimplemented. The report should be treated as a release blocker for any claim of encrypted sync, signed remote rules, complete deletion, or complete export.

## 3. Offline reliability findings

- **O-01 — No multi-device conflict mechanism (High, certain if sync is added).** Spec sections: Offline behavior and Cryptography. The app is currently local-only, so there is no sync queue, conflict resolver, device identity, or merge policy. The specification requires conflict behavior but supplies only a future-level description. Test two devices editing the same plant, stage event, and journal entry while offline; define append-only event merging and explicit conflict UI before sync ships.
- **O-02 — Clock skew can change compliance and dates (Medium, likely).** Spec sections: Offline behavior and Rule pack integrity. Records use `Date()` throughout, with no trusted time source, monotonic sequence, or clock-change detection. Test moving the device clock forward/backward across stage, reminder, withdrawal, rule-expiry, and export dates. Preserve event creation time separately from user-entered effective time where correctness matters.
- **O-03 — Partial writes and storage-full behavior are not specified (Medium, possible).** Spec sections: Offline behavior and Data at rest. Some writes use `try? context.save()` and photo writes use atomic files, but failures are swallowed in many paths. Test a full filesystem during a photo, harvest, feed, and multi-record save; verify no orphaned photo, half-created record, or misleading success state remains.
- **O-04 — Rule freshness offline is only static fallback today (High, certain for remote-rule requirement).** Spec sections: Rule pack integrity and Offline behavior. The bundled rule pack has a fixed version/date and no remote verification path. Test 30 days offline, a stale pack, a malformed signed pack, a valid stale pack, a jurisdiction mismatch, and a downgrade attempt. The app should retain the last verified compatible pack and visibly mark it stale.
- **O-05 — Local persistence is not a tested recovery protocol (Medium, unknown).** Spec sections: Offline behavior and Data at rest. SwiftData saves are frequently ignored with `try?`, and no migration, corruption, interruption, or recovery test is present in the repository. Test termination during saves, migration from every prior schema, corrupted store, read-only store, and restoration from a protected backup.
- **O-06 — Compliance status is derived from current local records without an audit snapshot (Medium, likely).** Spec sections: Offline behavior and Rule engine. The repository has a `ComplianceEngine`, but no persisted compliance snapshot or alert history matching the specification's model. Test rule changes, plant edits, deletions, and offline date changes; ensure a historical status remains reproducible and a current status is labeled with the rule-pack version.
- **O-07 — Notification queues can replay stale tasks after offline edits (Low to medium, possible).** Spec sections: Offline behavior and Notification privacy. Local notification requests are scheduled/cancelled, but no queue version or reconciliation record is described. Test changing a reminder offline, deleting its room, changing quiet hours, and reconnecting or relaunching; no obsolete notification should fire.

## 4. Metadata and E2EE analysis

### What exists today

The current repository appears to perform no network synchronization, remote rule fetch, analytics, crash reporting, or third-party telemetry. That minimizes provider-visible metadata today, but it is not the same as delivering the specification's encrypted cloud sync or signed CDN rule-pack commitments. The only explicit external-style operation is optional approximate location resolution through Core Location and reverse geocoding; the repository does not show an app-owned network request or storage of raw coordinates.

### What a future MVP provider could learn

If encrypted sync is implemented without E2EE, the provider could still see account/device identifiers, record counts, object types if not padded, record sizes, upload/download times, room or zone identifiers, conflict frequency, deletion tombstones, and access patterns. A sequence of stage, feed, environment, and harvest writes could reveal grow activity, approximate plant count, room occupancy, and harvest timing even when values are encrypted. The specification itself acknowledges visible metadata in the future E2EE section, but it does not define padding, batching, retention, identifier rotation, or a provider threat model.

Interim mitigations should include no analytics identifiers, opaque per-install identifiers, batching writes, minimizing server-side record types, padding or grouping sensitive records where practical, short retention, documented provider access controls, and an early E2EE design rather than treating it as a later migration. The product should not describe the provider as unable to read the data until keys are demonstrably unavailable to it.

### Rule-pack integrity

The bundled `RulePack` is deterministic and useful offline, but it is not a signed remote content pipeline. A valid signature on a stale or downgraded payload would be dangerous unless the app compares monotonic version, effective date, jurisdiction code, expiry, and a locally stored highest-accepted version. Canonical serialization and bounded decoding are required to avoid signature ambiguity and resource-exhaustion payloads.

### Store separation

The cultivation store and personal effect journal separation described in the specification is not implemented as a second store in the current repository; the repository contains cultivation `JournalEntry` records linked to plants/rooms, but no separate `PersonalEntry` model or store. The current photo store is shared by cultivation journal photos. This is not necessarily a defect for the current feature set, but it means the future personal journal claim must not be made until separate keys, filenames, caches, search indexes, exports, and deletion semantics are built and tested.

## 5. Test plan

1. **App-lock fail-closed test:** Disable device passcode/biometry in a controlled test environment, enable app lock, background and relaunch. Pass if no path clears the cover without authenticated device-owner authentication.
2. **Protected notification test:** Enable app lock, turn off generic-content preference, schedule every notification category, and inspect lock screen, notification center, summaries, Focus, CarPlay, and device logs. Pass if no plant, room, metric, product, or harvest name appears while protected.
3. **Export model-completeness test:** Create one record of every SwiftData model, export with and without journal/photos, and compare expected model names/counts to JSON, CSV, and README. Pass if every supported record is represented and optional journal behavior is exact.
4. **Delete-all completeness test:** Create every model, photos, cache entries, notifications, settings, and exports; run delete-all; reopen the app and inspect Application Support, caches, UserDefaults, pending notifications, and the store. Pass if all in-scope local records and files are gone and the UI explains any out-of-scope backup/export copies.
5. **Photo privacy test:** Import an image containing GPS EXIF, inspect both display and thumbnail bytes, load/cache them, delete the journal entry, and run delete-all. Pass if EXIF is absent, both files and cache entries are removed, and no orphan remains.
6. **Rule-pack adversarial test:** Feed the parser valid, malformed, oversized, stale, downgraded, wrong-jurisdiction, and correctly signed payloads. Pass if only a compatible, verified payload is accepted and the last verified pack remains available offline.
7. **Offline clock/storage test:** Change clock across week boundaries and rule expiry; fill storage during each atomic operation. Pass if records do not claim success after failed saves, no orphan files remain, and timestamps are labeled accurately.
8. **Sync threat-model test before implementation:** With two test devices, create simultaneous edits and append-only events offline. Pass criteria must be defined before coding: deterministic merge, no silent overwrite, visible conflict for ambiguous edits, and deletion tombstones that cannot resurrect data.
9. **Metadata review test:** Capture network traffic for any future sync/rule update build and inventory destination, identifiers, timing, sizes, and payload encryption. Pass if no plaintext grow content or stable unnecessary user identifier leaves the device.
10. **Authentication lifecycle test:** Exercise biometric success/failure, passcode fallback, lockout, enrollment change, rapid scene transitions, termination, multiple windows, and app-switcher screenshots. Pass if protected content is never exposed and the app never fails open.
11. **Dependency and release audit:** Generate a release dependency list, inspect linked frameworks, App Store privacy answers, entitlements, and diagnostics. Pass if the declared data practices match binaries and source.
12. **Legal-copy consistency test:** Compare in-app privacy/legal strings with actual capabilities. Pass if “no cloud sync,” “no analytics,” complete deletion, and location claims are either true for the build or removed/qualified.

## 6. Open questions

1. Is the intended product permanently local-only, or is encrypted cloud sync still a committed feature? If committed, what service and who controls keys?
2. What exact data is included in device backups and iCloud backups, and is exclusion or user-controlled backup required?
3. Is a separate personal-effect journal still planned? If so, what is its store boundary and access gate?
4. What is the authoritative rule-pack signing key, canonical payload format, rollback policy, and failure UI?
5. What are the required retention and deletion guarantees for exports saved in Files, crash reports, diagnostics, and backups?
6. Is approximate location required to store county/locality, or only a jurisdiction code? Is geocoding performed by Apple services under the intended privacy notice?
7. What is the threat model for a stolen device that was already unlocked, and should local app lock require a device passcode rather than allow disabling on an unprotected device?
8. Which features are allowed to appear in Spotlight, Siri, notifications, CarPlay, or future widgets?
9. Are treatment, equipment, service-history, and weekly-recap records in scope for export, delete-all, backup, and any future sync?
10. What legal basis and retention policy apply to age attestation, jurisdiction, approximate location, and cultivation records in each launch state?

## 7. Items for legal review

- Whether cultivation records, jurisdiction, location, harvest, and treatment data fall under CCPA/CPRA, Washington My Health My Health Data Act, Colorado or other state consumer-health-data regimes, and what notices/rights are required.
- Whether age attestation triggers COPPA or other age-assurance obligations, and whether the product should collect or retain any age signal at all.
- Whether Face ID usage and app-lock disclosures create any BIPA or biometric-privacy notice obligations; the implementation should state that biometric templates never enter the app.
- Apple App Store privacy-label accuracy for local storage, photos, location, diagnostics, exports, and any future sync provider.
- Whether deleting local records can be represented as “delete everything” when Apple backups, user-created exports, or future cloud copies remain outside app control.
- Whether rule citations, jurisdiction data, educational content, and future breeder/product references create legal or regulatory exposure.
- Whether any future sharing, community, recommendation, sensor, or analytics feature could facilitate sales, transfer, interstate transport, or diversion, and what controls/disclaimers are required.


## 8. Status of the findings in the current branch

This addendum records what the code does now. It does not change the original
findings, which describe the state at the time of the review.

- **F-03 — resolved.** `AppLock.requestUnlock` keeps the cover up when device-owner
  authentication cannot be evaluated; there is no path that clears the lock
  without a successful authentication.
- **F-04 — resolved.** Every model in the schema is now covered by export, backup,
  restore and delete-all through a single inventory (`Services/DataInventory.swift`),
  and a test fails if a model is added without coverage.
- **F-05 — resolved in copy.** Delete-all reports a verified zero count and states
  that Files exports and device or iCloud backups are outside the app.
- **F-06 — partly resolved.** Photos and the store directory keep complete file
  protection, and restore writes with `.completeFileProtection`. Verification on a
  locked device is still a device-level test.
- **F-08 — resolved.** New archives use a versioned envelope with PBKDF2-HMAC-SHA256
  at 210,000 iterations, a random salt, AES-GCM and bounded decode parameters;
  the legacy envelope remains readable.
- **F-11, F-13 — resolved.** Lock-screen copy stays generic whenever app lock is on,
  independent of the generic-content preference.
- **F-17 — resolved by removal.** The unused API-key helper was deleted.
- **F-01, F-02 — resolved in claims, not in capability.** The sync screen no longer
  presents a sync state, and sharing no longer creates or revokes "shares"; both
  screens state that the capability is absent.

The legal questions in section 7 are consolidated, with their dispositions, in
`docs/LEGAL_REVIEW.md`.
